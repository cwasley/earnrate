# earnrate

Rewards rules engine: given a merchant (plus optional amount and channel), pick the card that earns the most, from every card or the user's own, and explain why. Exposed as a CLI, a local MCP server, the hosted server at mcp.earnrate.dev and the website earnrate.dev.

The maintainer's full spec (data model, golden tests, milestones, competitive landscape) is `private/PROJECT_CONTEXT.md`, a separate private repo checked out inside this one and ignored by it. Read the relevant section before starting a milestone when it's there. This file is only the summary.

## Hard rules

- Never store or handle card numbers, CVVs, expiry dates or bank logins. Cards are product IDs only (`amex-gold`).
- No Plaid, no payments, no checkout automation, no browser extension in v1.
- Card earn rates live in data files with `last_verified` and `source_urls`. Never hardcode a rate in engine code. Facts shared across cards live in data too: memberships (names, the Costco fee and the stores that imply it, BofA tiers as a group) in `data/memberships.yaml`, issuer names and search words in `data/issuers.yaml`, travel sites as merchant `kind`, and "on"/"at" wording as category `preposition`.
- Don't invent rates. If a rule is ambiguous, leave a TODO and ask. Wrong rates are worse than missing ones.
- Matching and math are pure and deterministic. The LLM is only a cached, labeled fallback for merchant → category.
- Every recommendation states its matched rule, assumptions and confidence.
- Cards are optional. No command, MCP tool or page may require the user to enter any: with no cards, answer from every card earnrate knows; with cards named for one answer (`--cards`, the MCP `cards` input), use only those; a saved wallet adds tracking. The hosted connector signs in once when it's added, to an anonymous wallet that may stay empty (Collin's call, 2026-10-31); the CLI, local MCP server and earnrate.dev need no sign-in. Spending is optional too (typical amounts, said so). Statements stay CLI-only.

## Tooling

- Node >= 24 runs `.ts` files directly (type stripping), so development has no build step. Use only erasable TS syntax: no `enum`, `namespace` or parameter properties. Import local files with the `.ts` extension.
- The npm package is built JS: Node won't strip types inside `node_modules`. It supports Node 22 and up (`engines`), and CI smoke-tests the packed package on Node 22, so don't use newer Node APIs in `src/` without raising both. `yarn build` (`tsconfig.build.json`) emits `dist/` with `.ts` imports rewritten, and `yarn smoke:pack` installs the packed tarball in a temp dir and runs `earnrate`, `earnrate mcp` and `earnrate-mcp`. Paths built from `import.meta.url` must resolve the same from `src/` and `dist/`.
- TypeScript is pinned to `~6.0` because typescript-eslint doesn't support 7.x yet.
- `yarn validate` runs typecheck, lint, format check and tests. Run it before committing.
- `yarn earnrate <merchant> [amount]` runs the CLI (`src/cli/bin.ts`) against `$EARNRATE_WALLET` or `~/.earnrate/wallet.yaml`. CLI output is snapshot-tested against `wallet.example.yaml`, so a data or wording change shows up as a snapshot diff: review it, then `yarn vitest run -u`.
- `earnrate import` (`src/cli/import.ts`, `src/import/`) reads Amex and Chase activity CSVs. Don't add PDF statement parsing: Chase PDFs carry the full card number. Never copy a real statement into the repo, tests or fixtures; `tests/import.test.ts` uses synthetic CSVs, and its privacy test checks that only cap totals and hashes are written.
- Wallet file edits (`src/data/wallet-edit.ts`) splice lines into the user's YAML and must re-parse to exactly the expected wallet before the atomic rename. Never re-serialize the wallet: it drops the user's comments. The CLI and the MCP server change a saved wallet only through a `WalletStore` (`src/data/store.ts`), except `earnrate import --apply`, which writes its totals with `writeProgress`: `FileWalletStore` (`src/data/file-store.ts`, the YAML file) or `JsonWalletStore` (JSON in a key-value backend, Node-free; the hosted server's vaults use it). The add/update/remove/memberships/point-values rules live in `src/engine/wallet-change.ts` (also used by the browser wallet on earnrate.dev) and the purchase rules in `src/engine/record.ts` (pure).
- Freedom Flex's quarterly cap is `rotating: true`. When Chase posts a quarter (about two weeks before it starts), add its rules on that cap with `valid_from`/`valid_to`, `activate_by` (Chase's activation deadline) and evidence; until then answers warn that the quarter is missing.
- `plugin/` is the Claude plugin (Claude Code and Cowork). Its `.mcp.json` connects to the hosted server at `https://mcp.earnrate.dev`; it installs and runs nothing locally. `.claude-plugin/marketplace.json` lets people install it from this repo. Check it with `claude plugin validate --strict ./plugin`. Its README must say everything the plugin runs, sends, stores or fetches.
- `chatgpt/` is the ChatGPT plugin-directory package (`plugin.json` with the listing and the reviewers' test cases, `mcp.json` pointing at the hosted server with OAuth); `yarn chatgpt:pack` writes `earnrate-chatgpt.zip` for OpenAI's portal, and `tests/chatgpt.test.ts` keeps it within OpenAI's limits and in step with the catalog and tools. Server changes reach ChatGPT through OpenAI's daily scan (new tools wait for approval); listing or test-case changes need a new ZIP with a version bump. The hosted server serves the portal's domain token from the `OPENAI_APPS_CHALLENGE` secret at `/.well-known/openai-apps-challenge`. OpenAI's listing rules forbid comparing with other products, so the benchmark stays out of it.
- `mcpb/manifest.json` describes the Claude Desktop bundle; its `tools` list must match the local server's tools (14; the hosted server adds 4 account tools for 18) and its `prompts` list the server's prompts (`PROMPTS` in `src/mcp/prompts.ts`, 4) (`yarn smoke:mcpb` checks the built bundle, `tests/mcp.test.ts` the manifest). Keep new MCP tools and prompts in it.
- `yarn mcp` runs the MCP server (`src/mcp/bin.ts`, stdio; never write to stdout there). `tests/mcp.test.ts` drives it with an in-process client plus one real stdio round trip.
- The Claude merchant fallback is tested only with fake classifiers (`tests/llm.test.ts`). Never call the real API from tests.
- When a card's `todo:` is something the engine or schema can't express (not a data gap), also add it to `docs/feature-gaps.md`.
- Card checks cover every page the issuer publishes about the card (marketing page, rates and fees, rewards and offer terms, FAQ), and `source_urls` lists each one the source check can read, so the fine print is watched too. `verified_by` names who last checked every rule, fee and offer against all of them. Claude does these checks; ask Collin only about real ambiguities in the issuer's text or pages Claude can't read (bot protection, PDFs), saying exactly what to look at. Keep it cheap: when the weekly check opens a `card-sources` issue, re-check only the flagged card and page; do a full pass only for a new card, an issuer redesign, or about once a year.
- Every card rule needs an `evidence` quote (3–20 words) from one of the card's `source_urls`; integrity tests enforce it. That includes every card's required `foreign_transaction_fee` (a percent, `0` for none; `null` only with a `todo` when no readable issuer page states it), quoted as `rule: foreign_transaction_fee` from the rates-and-fees table, and each spend milestone (`milestones:`, evidence `rule:` is the milestone id). Quotes match the page's text, collapsed and hidden sections included, but never script or other embedded page data, where issuers leave stale copy; a quote a popup builds from that data on click takes `in_popup: true`, set only after seeing it in the open popup. After changing a card, run `yarn check-sources --update --cards <ids>` (just those cards' pages; drop `--cards` for a full pass) to refresh `data/sources.lock.json`. Amex rate-limits long runs with a "Loading Error" page; the checker counts that as unreachable and keeps the page's old lock entry. The weekly issue lists every page it couldn't read, with its cards and quotes: Claude and Collin re-read those in a headed browser. `src/sources/` is the checker; it commits only hashes of issuer text. A local `--update` also saves the earning lines' wording to the gitignored `.sources-cache.json`, so the next local run shows which lines disappeared, not just how many.
- Every change under `data/` is a data release: bump `data/VERSION` (`YYYY.MM.DD`, `.N` for another the same day), add its section to `data/CHANGELOG.md` (prose), and add the same release to `data/changes.yaml`, the structured record that `/changes`, its RSS feed, the card pages' "Recent changes" and `/companies` are built from. Each entry names its card(s) or merchants, categories, currencies, memberships or issuers, the `field` path (`welcome_offer`, `rules.<id>`, `credits.<id>.valid_to`), a `cause` and, where they're values, `was` and `now` as written in the data file. `cause: issuer` only when the issuer changed a term after earnrate had recorded the old value correctly: it needs one card, `was`, `now` and the issuer `source`, plus `detected` (the day the source check or a person first saw it) and `effective` (when the issuer says it took effect) when known; never guess either. A term earnrate starts recording late is an `addition`; earnrate's mistakes are `correction`; notes and names are `wording`; evidence and source URLs are `quote`; `verified_by`/`last_verified` are `review`. Those need a `summary`. `tests/changes.test.ts` holds the record to the changelog, `data/VERSION` and the data: every id and field exists (or a later entry removes it), and the newest `now` for a field still matches the card file.
- earnrate.dev (`site/`) is a static Vite + Preact app that runs the engine in the browser. `site/vite.config.ts` builds the card data into the bundle as `virtual:catalog`, so engine code used by the site must stay free of Node imports (only `src/data/`, `src/merchants/cache.ts` and `src/merchants/missed.ts` may use them). `yarn site:dev` runs it locally, `yarn site:build` writes `site-dist/`, and `yarn site:deploy` builds and deploys to Cloudflare. `yarn site:preview` deploys the checked-out branch's build to preview.earnrate.dev (`wrangler.preview.jsonc`, `site/preview-worker.ts`: noindex, nothing counted, no IndexNow) for Collin to review on his phone before it ships; only the main session runs it, from the branch's worktree. Nothing the visitor types may leave the browser: no fetches, and searches go in the URL fragment only. The first exception (Collin's call, 2026-11-03) is the cheat sheet's Add to Apple Wallet form, which posts only card ids, picks, activations, checkout labels, memberships and the date to `pass.earnrate.dev`; never add spending, searches or anything else to it, and say so on the privacy page if that ever changes. The second exception (Collin's call, 2026-11-04) is usage counting: `site/app/track.ts` beacons an event name from `EVENTS` in `site/events.ts` (at most once per page load) to `/count`, where `site/worker.ts` writes the name and a coarse device kind to Analytics Engine (`earnrate_site_usage`). Never send a search, card, amount, setting or id, never keep an IP or user agent, and add any new event to the privacy page's list (a test checks it). The third, opt-in exception (Collin's call, 2026-11-06) is wallet sync with Claude: with sync on, the wallet (cards, picks, activations, memberships, point values, cap and spend totals, credits and free nights used and not used, opening dates, issuers left out of next-card answers) goes to mcp.earnrate.dev and is stored encrypted like the connector's; a recorded purchase is sent so its totals update, and only the totals are kept. Searches, stores and amounts asked about still never leave the browser, and answers are still computed in it. `site/api.ts` is that path: `/api/connect` and `/api/callback` sign in as the fixed public client `earnrate-site` (PKCE; `remote/src/site-client.ts`), the tokens live only in an HttpOnly, Secure, SameSite=Strict cookie scoped to `/api` (never a response body, a URL the page reads, or page storage: the site has no script-src policy), `/api/wallet` forwards GET and one change to the hosted server over the `MCP` service binding (refreshing the token as needed), and `/api/disconnect` ends that browser's connection. Wallet requests need the `x-earnrate-sync` header and a same-origin request. The site Worker runs only for `/count` and `/api/*` and stays stateless: no KV, Durable Object or D1, only the service binding (`tests/site-count.test.ts` pins both configs; `tests/site-api.test.ts` drives the flow against an in-memory hosted server). The preview has the same `/api/*` against the live hosted server. Home-page links and buttons name their event in `data-count`. `scripts/build-pages.ts` (run by `yarn site:build`) also renders static search pages, `/best/<store>`, `/best/<category>` and `/cards/<card>`, card-vs-card pages at `/compare/<a>-vs-<b>` (ids in alphabetical order; `scripts/compare.ts` holds the pair rule and each page's facts, and the reverse order redirects through the generated `_redirects`), plus `sitemap.xml` and `robots.txt`. Page types beyond those live in `scripts/pages/` (one module each: `quarterly.ts` for `/quarterly/`, `coding.ts` for `/how-stores-code` and the stores' "How it codes", `fee-worth.ts` for the card pages' annual-fee math, `categories.ts` for `/categories/`, `changes.ts` for `/changes`, `/changes.xml` and the card pages' "Recent changes"), sharing `layout()` and the breadcrumbs in `site.ts`; every sentence on them comes from card data, merchant data or the engine. Titles stay within 60 characters and descriptions within 155 (`fitTitle`/`fitDescription`, held by `tests/pages.test.ts`, which also builds the pages and fails on a link to a missing page). A store page is indexed only when it says something its category page doesn't (`scripts/pages/indexing.ts`: notes on how it codes, a credit, a store card, terms naming it, cards it refuses, or a ranking of its own); the rest are `noindex, follow` and out of the sitemap, and category pages list every store that codes as them. Card, store and comparison pages pick their next-step buttons in the browser from the saved wallet (`scripts/pages/actions.ts`, read only, nothing sent), and the app counts the arrival (`page-*` events). The build draws a 1200x630 preview image per card and store page in Chromium (`scripts/pages/og.ts`, cached in `node_modules/.cache/earnrate-og`; `EARNRATE_OG=off` skips them, `CHROMIUM_PATH` picks another Chromium). A page's sitemap `lastmod` is when its facts last changed in git (`scripts/lastmod.ts`: a card page follows its card file, a comparison the later of its two, rankings follow `data/`), never the build date, and `yarn site:deploy` ends by sending pages whose `lastmod` changed to IndexNow (`scripts/indexnow.ts`; the key file is `site/public/<key>.txt`, and the gitignored `.indexnow-sent.json` remembers what this machine sent). They state current rates and quarterly bonuses publicly, so redeploy the site after every data change and when a quarter turns over. The home page's counts, sample cheat sheet and quoted answer are filled in at build time by `scripts/landing.ts` (the `<!--earnrate:…-->` placeholders in `site/index.html`), and `node scripts/make-images.ts` redraws the icons, `favicon.ico`, the Desktop bundle icon and the social preview. The comparison app renders inside the home page, so the page's own CSS is scoped to `main > section` and home-page-only class names; check the app's class names (`class=` and `className=`) before adding a global rule. Cards are drawn, never shown with issuer card art: `src/format/card-art.ts` draws a plain card in the card's `color` (or its issuer's), used by the app (`CardArt.tsx`) and the static pages. The service worker (`site/public/sw.js`) serves the manifest and icons network-first; bump its `CACHE` name when changing what it pre-caches, and the `?v=N` on icon links when the icons change.
- `pass/` is the Apple Wallet pass signer at `pass.earnrate.dev`, a stateless Cloudflare Worker (no storage bindings, observability off; a test checks the config): `pass/src/pass.ts` builds the cheat-sheet pass from the engine (rates never come from the request), `sign.ts` zips it with a SHA-1 manifest and a detached PKCS #7 signature, and `app.ts` validates the form (`PassWalletSchema`, known card ids, 16 KB) and refuses with 503 until its secrets are set (`PASS_TYPE_ID`, `TEAM_ID`, `PASS_CERT_PEM`, `PASS_KEY_PEM`, `WWDR_PEM`; the key and certificates live in the gitignored `private/apple-pass/`). Passes expire at the quarter's end and have no update service. It counts `pass-made` and `pass-refused:<status>` with the device kind in the site's dataset. `yarn pass:check` bundles it and `yarn pass:deploy` deploys it; `node scripts/make-images.ts` draws `pass/assets/`. The Pass Type ID certificate expires yearly: renew it on developer.apple.com and reset the secrets.
- `remote/` is the public remote MCP server at mcp.earnrate.dev, a Cloudflare Worker serving the same `createEarnrateServer` over Streamable HTTP (`savedWallets: 'account'`), so the server's import graph must stay free of Node imports too (import the `Catalog` type from `src/schema/catalog.ts`, not `src/data/load.ts`). It also serves earnrate.dev's synced wallet: `GET /wallet` (what `list_wallet` gives) and `POST /wallet/changes` (one change, `{"tool": ..., "input": ...}`, run by the MCP tool's own handler from `src/mcp/wallet-api.ts`, so the rules and refusal text match; `import_wallet` with its `replace` confirmation is the only whole-wallet write), behind the same token check, rate limit and `checkIn`, and `POST /wallet/sign-out`, which ends only that connection. earnrate.dev's client is fixed in code (`remote/src/site-client.ts`, answered in place of a KV registration), and no other app may register a callback on earnrate.dev. Every request needs a token: without one, or for a wallet that's gone, `remote/src/app.ts` answers 401 and Claude opens `/authorize` (`remote/src/auth.ts`, `pages.ts`), where the user starts an anonymous wallet or reconnects one with its recovery code. Only while sign-in itself is down are questions answered signed out. The code is typed only on that page, never in chat; `switch_wallet` signs the app out so the user can connect another wallet. The sign-in pages run one script, allowed by its CSP hash (`PAGE_SCRIPT_HASH`). Each wallet is one Durable Object (`vault.ts`), AES-GCM encrypted with its own key, which only the recovery code or the sign-in grant can unwrap (`vault-crypto.ts`); it deletes itself 13 months after last use (any tool call counts, via `checkIn`), or after a week if it was never used. `@cloudflare/workers-oauth-provider` is the authorization server (KV `OAUTH_KV`); vitest aliases its `cloudflare:workers` import to `tests/stubs/`. `yarn remote:build` writes `remote/catalog.gen.json` (the card data, imported as `earnrate:bundle`), `yarn remote:check` bundles it without deploying (CI runs it) and `yarn remote:deploy` deploys it; redeploy it with the site after data changes. It keeps no request logs, rate-limits per IP (and the sign-in page more tightly), and counts only method and tool names, tool refusals by tool name, server errors by path, `wallet-created` and `wallet-active` (a vault's once-a-day check-in write), each with the kind of app (`appKind` in `remote/src/auth.ts`, from the client's id and redirect hosts, never its self-chosen name; the live check is `check`, earnrate.dev's sync `site`), in Analytics Engine (`tests/remote.test.ts`). `yarn usage` prints a week of all these counts. Its retention numbers and rate-limit window live in `remote/src/policy.ts` (the limits per window in `remote/wrangler.jsonc`); `tests/repo.test.ts` checks the privacy page, terms and READMEs state them, and that the docs' card and tool counts match the catalog and tool lists. `node scripts/live-check.ts` checks the live site and server end to end (signs in as a new client, saves a card, deletes the wallet); `.github/workflows/live-check.yml` runs `--quick` hourly (pages, offline files, the sign-in gate; label `uptime`) and the full check daily (also a browser load of earnrate.dev that fails on page errors, and the server's error counts from Analytics Engine via the `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` secrets; label `live-check`). A failure opens an issue assigned to the owner, so GitHub emails Collin, and it closes when that check passes again. GitHub runs scheduled workflows hours late, so `monitor/` (a cron-only Worker, `yarn monitor:deploy`, secret `GH_DISPATCH_TOKEN`: a fine-grained token for this repo with Actions read and write) dispatches both checks on time and a quick one within minutes of a failed probe; the daily check fails if it stops dispatching.
- Spend milestones count only when the wallet's `milestone_usage` shows a purchase crossing the total, never from assumed spending. Their points count toward the ranking, but `RankedCard.effectiveReturnPct` and `earned` are the card's own rate; the bonus is `milestoneBonus` and its own line. Abroad (`country` other than `US`), ranking is net of `foreign_transaction_fee`; the site sends the unassigned code `ZZ` and never prints it.
- Shared wording and math live in one place: `src/engine/text.ts` (money, dates, period words, lists), `src/engine/compare.ts` (EPSILON, the "close to the best card" rule), `src/engine/offers.ts` (offer terms), `src/engine/memberships.ts`, and `EVERYDAY_PURCHASES` in `src/engine/cheat-sheet.ts`. Use them rather than formatting inline.
- Tests: vitest, in `tests/` (golden cases in `tests/golden/`) or next to the source as `*.test.ts`.

## Releasing

1. Bump `version` in `package.json`, both versions in `server.json` and the one in `mcpb/manifest.json` (tests keep them in step), commit and push. The plugin has its own version: it holds no earnrate code, only the hosted server's address, so bump `plugin/.claude-plugin/plugin.json` only when files under `plugin/` change. The plugin directory scans each push that changes it; with auto-publish on, a version that passes its checks goes live. The connector listing needs nothing for server changes, except a listing edit (reviewer-approved) when tool names change.
2. Create a GitHub release tagged `v<version>`. `.github/workflows/release.yml` validates, checks the tag, and runs `npm stage publish --provenance` through npm trusted publishing (no npm token in the repo), then builds `earnrate.mcpb` (the Claude Desktop one-click install, `yarn mcpb:pack`), smoke-tests it and attaches it to the release.
3. Collin approves the staged version on npmjs.com (Staged Packages) with 2FA. Nothing is live until then.
4. Once `npm view earnrate version` shows it, `mcp-publisher publish` updates the MCP registry entry, including the hosted server in `remotes`.
