# earnrate

Rewards rules engine: given a merchant (plus optional amount and channel), pick the card that earns the most, from every card or the user's own, and explain why. Exposed as a CLI, a local MCP server, the hosted server at mcp.earnrate.dev and the website earnrate.dev.

The maintainer's full spec (data model, golden tests, milestones, competitive landscape) is `private/PROJECT_CONTEXT.md`, a separate private repo checked out inside this one and ignored by it. Read the relevant section before starting a milestone when it's there. This file is only the summary.

## Hard rules

- Never store or handle card numbers, CVVs, expiry dates or bank logins. Cards are product IDs only (`amex-gold`).
- No Plaid, no payments, no checkout automation, no browser extension in v1.
- Card earn rates live in data files with `last_verified` and `source_urls`. Never hardcode a rate in engine code. Facts shared across cards live in data too: memberships (names, the Costco fee and the stores that imply it, BofA tiers as a group) in `data/memberships.yaml`, issuer names and search words in `data/issuers.yaml`, travel sites as merchant `kind`, and "on"/"at" wording as category `preposition`. A category bought only on a website or app says so (`channel: online`, on `online_retail`): a purchase there counts as an online one unless the person says it's in store, and the answer says it assumed so.
- Don't invent rates. If a rule is ambiguous, leave a TODO and ask. Wrong rates are worse than missing ones.
- Matching and math are pure and deterministic. The LLM is only a cached, labeled fallback for merchant → category.
- Every recommendation states its matched rule, assumptions and confidence.
- Cards are optional. No command, MCP tool or page may require the user to enter any: with no cards, answer from every card earnrate knows; with cards named for one answer (`--cards`, the MCP `cards` input), use only those; a saved wallet adds tracking. The hosted connector signs in once when it's added, to an anonymous wallet that may stay empty (Collin's call, 2026-10-31); the CLI, local MCP server and earnrate.dev need no sign-in. Spending is optional too (typical amounts, said so). A statement is read only on the person's device: by the CLI, or by earnrate.dev's `/statement` page, which can't send it anywhere (below). Never by the hosted server, a Claude or ChatGPT tool, or any page that can make a request.

## Tooling

- Node >= 24 runs `.ts` files directly (type stripping), so development has no build step. Use only erasable TS syntax: no `enum`, `namespace` or parameter properties. Import local files with the `.ts` extension.
- The npm package is built JS: Node won't strip types inside `node_modules`. It supports Node 22 and up (`engines`), and CI smoke-tests the packed package on Node 22, so don't use newer Node APIs in `src/` without raising both. `yarn build` (`tsconfig.build.json`) emits `dist/` with `.ts` imports rewritten, and `yarn smoke:pack` installs the packed tarball in a temp dir and runs `earnrate`, `earnrate mcp` and `earnrate-mcp`. Paths built from `import.meta.url` must resolve the same from `src/` and `dist/`.
- TypeScript is pinned to `~6.0` because typescript-eslint doesn't support 7.x yet.
- `yarn validate` runs typecheck, lint, format check and tests. Run it before committing.
- `yarn earnrate <merchant> [amount]` runs the CLI (`src/cli/bin.ts`) against `$EARNRATE_WALLET` or `~/.earnrate/wallet.yaml`. CLI output is snapshot-tested against `wallet.example.yaml`, so a data or wording change shows up as a snapshot diff: review it, then `yarn vitest run -u`.
- `earnrate import` (`src/cli/import.ts`, `src/import/`) reads Amex and Chase activity CSVs. Don't add PDF statement parsing: Chase PDFs carry the full card number. Never copy a real statement into the repo, tests or fixtures; `tests/import.test.ts` uses synthetic CSVs, and its privacy test checks that only cap totals and hashes are written.
- Wallet file edits (`src/data/wallet-edit.ts`) splice lines into the user's YAML and must re-parse to exactly the expected wallet before the atomic rename. Never re-serialize the wallet: it drops the user's comments. The CLI and the MCP server change a saved wallet only through a `WalletStore` (`src/data/store.ts`), except `earnrate import --apply`, which writes its totals with `writeProgress`: `FileWalletStore` (`src/data/file-store.ts`, the YAML file) or `JsonWalletStore` (JSON in a key-value backend, Node-free; the hosted server's vaults use it). The add/update/remove/memberships/point-values rules live in `src/engine/wallet-change.ts` (also used by the browser wallet on earnrate.dev) and the purchase rules in `src/engine/record.ts` (pure).
- Freedom Flex's quarterly cap is `rotating: true`. When Chase posts a quarter (about two weeks before it starts), add its rules on that cap with `valid_from`/`valid_to`, `activate_by` (Chase's activation deadline), `activate_from` (when activation opens, if Chase's page says) and evidence; until then answers to the card's holders (a saved wallet or cards named for the answer) and answers about the card itself warn that the quarter is missing; every-card answers leave it out (`heldRotationGap` in `src/engine/rotation.ts`).
- A monthly credit that pays a different amount in some months says so (`month_amounts`, by month number: the Amex Platinum's Uber Cash is `{ 12: 35 }`), with a quote that names the month; every total, the to-do and the pages read the period's amount through `periodAmount` in `src/engine/credits.ts`.
- A credit earnrate can't tie to a purchase (an airline fee credit for the airline you choose, a credit on only some of a merchant's sales) is listed, not matched: `listed: { name, on }` in place of `match`, with a quote stating its amount. It shows on card and year-end pages, in the wallet and the to-do, and counts against a fee once the cardholder says they use it, but never appears in a purchase answer. Credits that pay only after other purchases, or per booking or stay, stay out (`docs/feature-gaps.md`).
- The typical month (`TYPICAL_MONTHLY_SPEND` in `src/engine/simulate.ts`) is behind every yearly figure given when no spending is. `tests/typical-shape.test.ts` fails when one of its lines can't reach a card's bonus rule for that kind of spending for a reason that isn't on its list, and `node scripts/typical-audit.ts` prints what each line reaches. Find a card saves spending rows only once the person changes one, and saved rows equal to a past default set (`PAST_TYPICAL` in `site/app/spending-rows.ts`) count as typical: when the defaults change, add the old set there.
- `plugin/` is the Claude plugin (Claude Code and Cowork). Its `.mcp.json` connects to the hosted server at `https://mcp.earnrate.dev`; it installs and runs nothing locally. `.claude-plugin/marketplace.json` lets people install it from this repo. Check it with `claude plugin validate --strict ./plugin`. Its README must say everything the plugin runs, sends, stores or fetches.
- `chatgpt/` is the ChatGPT plugin-directory package (`plugin.json` with the listing and the reviewers' test cases, `mcp.json` pointing at the hosted server with OAuth); `yarn chatgpt:pack` writes `earnrate-chatgpt.zip` for OpenAI's portal, and `tests/chatgpt.test.ts` keeps it within OpenAI's limits and in step with the catalog and tools. Server changes reach ChatGPT through OpenAI's daily scan (new tools wait for approval); listing or test-case changes need a new ZIP with a version bump. The hosted server serves the portal's domain token from the `OPENAI_APPS_CHALLENGE` secret at `/.well-known/openai-apps-challenge`. OpenAI's listing rules forbid comparing with other products, so the benchmark stays out of it.
- `mcpb/manifest.json` describes the Claude Desktop bundle; its `tools` list must match the local server's tools (14; the hosted server adds 4 account tools for 18) and its `prompts` list the server's prompts (`PROMPTS` in `src/mcp/prompts.ts`, 4) (`yarn smoke:mcpb` checks the built bundle, `tests/mcp.test.ts` the manifest). Keep new MCP tools and prompts in it.
- `yarn mcp` runs the MCP server (`src/mcp/bin.ts`, stdio; never write to stdout there). `tests/mcp.test.ts` drives it with an in-process client plus one real stdio round trip.
- The Claude merchant fallback is tested only with fake classifiers (`tests/llm.test.ts`). Never call the real API from tests.
- When a card's `todo:` is something the engine or schema can't express (not a data gap), also add it to `docs/feature-gaps.md`.
- Card checks cover every page the issuer publishes about the card (marketing page, rates and fees, rewards and offer terms, FAQ), and `source_urls` lists each one the source check can read, so the fine print is watched too. `verified_by` names who last checked every rule, fee and offer against all of them. Claude does these checks; ask Collin only about real ambiguities in the issuer's text or pages Claude can't read (bot protection, PDFs), saying exactly what to look at. Keep it cheap: when the weekly check opens a `card-sources` issue, re-check only the flagged card and page; do a full pass only for a new card, an issuer redesign, or about once a year.
- Every card rule needs an `evidence` quote (3–20 words) from one of the card's `source_urls`; integrity tests enforce it. A rule can also record the stores its issuer names as earning its rate or not earning it (`named: { earning, not_earning }`, merchant ids), with quotes under `<rule id>.earning` and `<rule id>.not_earning` that between them contain every listed store's name; the integrity check refuses a named store the rule's math contradicts, the store's page says what the issuer names and is indexed for it, and answers cite it. Add an issuer's list only from its own page, and never treat a list of examples as complete. That includes every card's required `foreign_transaction_fee` (a percent, `0` for none; `null` only with a `todo` when no readable issuer page states it), quoted as `rule: foreign_transaction_fee` from the rates-and-fees table, and each spend milestone (`milestones:`, evidence `rule:` is the milestone id). Quotes match the page's text, collapsed and hidden sections included, but never script or other embedded page data, where issuers leave stale copy; a quote a popup builds from that data on click takes `in_popup: true`, set only after seeing it in the open popup. Offer quotes (`welcome_offer`, `not_with`, `first_year_fee`) match only the text the page shows, since issuers leave old offers in hidden markup; one in a section that opens on click (an accordion or overlay of offer details, a closed tab) takes `in_collapsed: true`, set only after seeing it there, and the report marks an offer quote found only in hidden text. After changing a card, run `yarn check-sources --update --cards <ids>` (just those cards' pages; drop `--cards` for a full pass) to refresh `data/sources.lock.json`. Amex rate-limits long runs with a "Loading Error" page; the checker counts that as unreachable and keeps the page's old lock entry. The weekly issue lists every page it couldn't read, with its cards and quotes: Claude and Collin re-read those in a headed browser. `src/sources/` is the checker; it commits only hashes of issuer text. A local `--update` also saves the earning lines' wording to the gitignored `.sources-cache.json`, so the next local run shows which lines disappeared, not just how many.
- Every change under `data/` is a data release: bump `data/VERSION` (`YYYY.MM.DD`, `.N` for another the same day), add its section to `data/CHANGELOG.md` (prose), and add the same release to `data/changes.yaml`, the structured record that `/changes`, its RSS feed, the card pages' "Recent changes" and `/companies` are built from. Each entry names its card(s) or merchants, categories, currencies, memberships or issuers, the `field` path (`welcome_offer`, `rules.<id>`, `credits.<id>.valid_to`), a `cause` and, where they're values, `was` and `now` as written in the data file. `cause: issuer` only when the issuer changed a term after earnrate had recorded the old value correctly: it needs one card, `was`, `now` and the issuer `source`, plus `detected` (the day the source check or a person first saw it) and `effective` (when the issuer says it took effect) when known; never guess either. A term earnrate starts recording late is an `addition`; earnrate's mistakes are `correction`; notes and names are `wording`; evidence and source URLs are `quote`; `verified_by`/`last_verified` are `review`. Those need a `summary`. `tests/changes.test.ts` holds the record to the changelog, `data/VERSION` and the data: every id and field exists (or a later entry removes it), and the newest `now` for a field still matches the card file.

GitHub runs scheduled workflows hours late, so `monitor/` (a cron-only Worker, `yarn monitor:deploy`, secret `GH_DISPATCH_TOKEN`: a fine-grained token for this repo with Actions read and write) dispatches both checks on time and a quick one within minutes of a failed probe; the daily check fails if it stops dispatching.
- Spend milestones count only when the wallet's `milestone_usage` shows a purchase crossing the total, never from assumed spending. Their points count toward the ranking, except that a card whose statement credit pays on the purchase moves above one that leads it only on a spend bonus (the bonus comes with a later purchase; the credit's period ends; Collin's call, 2026-11-08), and a welcome bonus behind pace never takes the pick from such a credit. `RankedCard.effectiveReturnPct` and `earned` are the card's own rate; the bonus is `milestoneBonus` and its own line. Abroad (`country` other than `US`), ranking is net of `foreign_transaction_fee`; the site sends the unassigned code `ZZ` and never prints it. When every card is ranked, a card whose `requires_membership` the user hasn't given (saved, passed, held, or implied by the store, as buying at Costco implies Costco's) is left out of the ranking and named after it, one line per membership and only where it would have placed (`missingMembership`, `ifMemberLines` in `src/engine/memberships.ts`; Collin's call, 2026-11-08).
- Shared wording and math live in one place: `src/engine/text.ts` (money, dates, period words, lists), `src/engine/compare.ts` (EPSILON, the "close to the best card" rule), `src/engine/offers.ts` (offer terms), `src/engine/memberships.ts`, and `EVERYDAY_PURCHASES` in `src/engine/cheat-sheet.ts`. Use them rather than formatting inline.
- Tests: vitest, in `tests/` (golden cases in `tests/golden/`) or next to the source as `*.test.ts`.

## Releasing

1. Bump `version` in `package.json`, both versions in `server.json` and the one in `mcpb/manifest.json` (tests keep them in step), commit and push. The plugin has its own version: it holds no earnrate code, only the hosted server's address, so bump `plugin/.claude-plugin/plugin.json` only when files under `plugin/` change. The plugin directory scans each push that changes it; with auto-publish on, a version that passes its checks goes live. The connector listing needs nothing for server changes, except a listing edit (reviewer-approved) when tool names change.
2. Create a GitHub release tagged `v<version>`. `.github/workflows/release.yml` validates, checks the tag, and runs `npm stage publish --provenance` through npm trusted publishing (no npm token in the repo), then builds `earnrate.mcpb` (the Claude Desktop one-click install, `yarn mcpb:pack`), smoke-tests it and attaches it to the release.
3. Collin approves the staged version on npmjs.com (Staged Packages) with 2FA. Nothing is live until then.
4. Once `npm view earnrate version` shows it, `mcp-publisher publish` updates the MCP registry entry, including the hosted server in `remotes`.
5. Redeploy the hosted server (`yarn remote:deploy`) and run `node scripts/live-check.ts`: it reports the version from `package.json` at build time (`list_wallet` says "Running earnrate <version>"), so until then it still names the previous release. The Claude plugin (`plugin/`) and the ChatGPT package (`chatgpt/`) keep their own versions.
